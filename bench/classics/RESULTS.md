# Classic apps: reason-react on React 18.3 vs Melact

Generated by `node bench/classics/run.mjs`. Each app is one `app.mlx`, compiled against reason-react
(React 18.3.1, production build) and against Melact, bundled by esbuild, and driven through its
`scenario.mjs` in headless Chromium (Playwright). Per step: median over the runs of the main-thread
busy time (CDP `TaskDuration` delta, from before the step until the page has settled: no DOM mutation
during two animation frames, a task and an idle callback), and of the `LayoutCount` and `RecalcStyleCount`
deltas. Runs per app: 5 at 1x; 5 at 4x except the apps marked with their run count.
Ratio is Melact / React; above 1 Melact is slower. DOM: the root's and the portal container's
markup after the step (attributes sorted, form fields' `value`/`checked` added), React's first run
against Melact's first run.

## Findings

Every finding has a minimal repro in [`repro/`](repro), runnable with `--apps=repro/<name>`; their numbers are
in [`repro/results.md`](repro/results.md). Causes are hypotheses from reading `react/runtime/instance.ml`,
`react/react.ml`, `melhole/runtime/view.ml`, `melhole/runtime/events.ml` and `melhole/compiler/`.

### Where Melact is slower

| finding | app steps (ratio 1x / 4x) | repro (1x) | likely cause |
|---|---|---|---|
| [`nested-context-consumers`](repro/nested-context-consumers) | jsontree collapse all 2.25 / 2.39, search typing 2.16 / 2.11, clear search 1.86 / 1.33 | 19,531 nested consumers: 65 vs 425 ms (6.5x); flat: 1.22x | a flush renders in rounds, one per level of dirty consumers; every round runs `ordered` again on all remaining dirty instances (front nodes, common ancestor by `contains`, a TreeWalker over its whole subtree), so the cost is depth × (consumers + DOM nodes) |
| [`effect-sort`](repro/effect-sort) | email switch folder 1.82 / 1.78, clear search 1.30 / 1.31 | 5000 memo rows with `useEffect` and a sibling with a hook: 33.6 vs 355.8 ms (10.6x) | when a pass put any instance off, `settle` sorts all four effect queues with `List.stable_sort earlier`; `earlier` calls `compareDocumentPosition` on siblings, which costs O(siblings) in Blink, so thousands of new rows cost O(n² log n) |
| [`unicode-layout-cost`](repro/unicode-layout-cost) (from `unicode-static-text`) | kanban mount 1.40 / 1.41, clear filter 1.37 / 1.34, expand 4 columns 1.32 / 1.07 | 3000 rows with static `{js\|→\|js}`: 63.9 vs 145.5 ms (2.3x), the difference is layout | static `{js\|…\|js}` text goes into the template as UTF-8 bytes read as Latin-1; the mojibake has C1 control characters, which Chromium lays out slowly |
| [`deferred-value`](repro/deferred-value) | playlist clear search 1.29 / 1.26 | erase 2 keys over 5000 rows: 1.14x (1x), 1.21x (4x); Melact faster on longer typing | `useDeferredValue` is the identity (`react/react.ml`), so every keystroke renders the whole list at once; React renders the deferred list in a background lane and drops a stale one |
| [`menu-measure`](repro/menu-measure) | feed hide 20 posts 1.37 / 0.96 (styles 40/60), outside click (styles 10/20) | open x20: style recalcs 20 vs 39 | a component that renders `React.null` gets an empty text node as a marker in `commit`; the insertion dirties style, so the layout read in its layout effect forces a recalc React does not do |
| [`list-in-match`](repro/list-in-match) | perhaps diff add 10 line comments 1.12 / 1.13, hide whitespace 1.19 / 1.17 | list inside a `match` branch: 0.89–0.96, against 0.16–0.23 for the same list directly in the hole | melact-ppx compiles `React.array (Array.map …)` to `View.each` only when it is the whole hole; inside a `match` it stays `React.array` through `set_content`. Not slower than React, but the compiled loop is lost |

Other steps above 1.05 last a few milliseconds (wizard, unmounts) or are within run-to-run noise; none has
a repro.

| finding | app steps (layouts R/M, styles R/M) | repro | likely cause |

### Behaviour that differs from React

| finding | where it shows | likely cause |
|---|---|---|
| [`set-state-in-render`](repro/set-state-in-render) | crash `melact: a state setter was called while a component was rendering` on React's documented "adjust state when a prop changes" pattern; the DOM stays stale | `Instance.invalidate` and `invalidate_state` raise whenever a component is rendering, also for that component's own state, which React allows and renders again at once |
| [`rows-context`](repro/rows-context) | dashboard switch theme: grid lines keep the old stroke | `Scope` records `let theme = React.useContext ctx` as a definition and `Free.closure` replaces `theme` by its reads (only the top-level context), so a keyed list whose rows read it gets `outer = no_inputs` and keeps its rows |
| [`select-value`](repro/select-value) | shop (sort select, 4 steps), settings (every step), wizard (back to step 1): a controlled `<select>` mounts showing the first option or none | the select's `value` hole is written before its options exist (option `value` is a property hole; mapped options mount later); React sets it after the children |
| [`stale-layout-read`](repro/stale-layout-read) | eventtable mount: error rows keep a stale `in-view` class | a component whose props are unchanged is not rendered again (every component behaves as memoized), so a body that reads layout through `ref.current` keeps the value it read at mount; React renders non-memo children again |
| [`radio-same-name`](repro/radio-same-name) | settings: radios stay unchecked after search results with the same `name` came and went | the `checked` hole is `===`-guarded and restored only after an `input`/`change` on that element; React assigns `checked` on every update |
| [`popover-focus`](repro/popover-focus) | a `useEffect` after a click sees the DOM of the next render, not of its own commit | as above |
| [`change-event`](repro/change-event) | a lone `change` event (testing-library's `fireEvent.change`) never reaches `onChange`; the scenarios of admin, shop, wizard, settings, calendar and eventtable send `input` then `change`, as a browser does | `onChange` is bound to `input` only (`melhole/compiler/dom_props`); React also listens to `change` |
| [`controlled-input-flush`](repro/controlled-input-flush) | an `input` event and then a `keydown` or `click` in the same task: the second handler sees the old state; the spreadsheet and virtuallist scenarios wait a frame between them, as a user would | React renders synchronously after an event on a controlled input; Melact renders in a microtask, which does not run between two `dispatchEvent` calls of one script |
| [`unicode-static-text`](repro/unicode-static-text) | calendar, chess, gantt, kanban and playlist differ in every step (`‹` becomes `â¹`) | `melhole/compiler/element.ml` takes the `Pconst_string`, drops its `js` delimiter and emits the template HTML as a plain string |
| attribute order | raw `innerHTML` of most apps | React writes props in the order of reason-react's `domProps`, Melact in source order; harmless, and the comparison sorts attributes |

### Measurement notes

- Other sessions ran Chromium benchmarks on the same machine during parts of the runs, and the machine slept
  during the 4x pass. Times are main-thread busy time, not wall time; React and Melact runs alternate and
  every number is a median. A single short step drifts by up to about 1.4x between runs.
- At first settling waited for a quiet DOM only, and React's time-sliced `useDeferredValue` render in playlist
  escaped the window ("clear search" showed 8.0x). Settling now also waits for an idle callback; playlist was
  measured again, and eventtable, jsontree, email and dashboard measured again showed no systematic shift.
- datagrid renders one page of 1,000 of its 10,000 rows; virtuallist keeps about 125 nodes by design.
