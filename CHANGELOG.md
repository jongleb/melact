# Changelog

- Milestone 1: `melact.view` (templates with holes, hole patcher, keyed reconcile, delegated events), `melact.program` sandbox, hand-written counter example, 26 vitest + jsdom tests.
- Milestone 2: component instances and hooks (`Hook` keys, `Component`, `Context`, microtask flush, effects), `React`, `ReactDOM.Client`; the same test suite passes against reason-react with React 18 and against melact.
- Milestone 3: `melact-ppx` for Reason, OCaml `[@JSX]` and mlx: one template per JSX tree, hook keys per call site, `[@react.component]` and signatures; expect tests in `test/ppx`.
- Runtime trimming: no `Printf`, `Hashtbl` or `Map` in the bundle; keyed lookup by sorted keys. The counter app went from 23.4 kB to 10.2 kB gzip.
- A runtime made of parts: every kind of child carries its own mount and patch code, every hole its own `put_*`, and the component scheduler is installed by the first component. Unused parts drop out of the bundle: the counter app is 5.7 kB gzip with Meltea and 7.5 kB with Melact.
- Compiled walks: the compiler writes out the `firstChild`/`nextSibling` walk to every hole and picks HTML or SVG parsing, so the runtime keeps no paths and no tag table. The counter app is 4.2 kB gzip with Meltea and 5.9 kB with Melact.
- Direct writes: the compiled walk makes typed holes once per clone and the refresh writes them with `set_text`, `set_attr` and friends; no binding table, no indices. The counter app is 4.0 kB gzip with Meltea and 5.7 kB with Melact.
- TodoMVC in Meltea (`examples/todomvc`): routing, editing, `localStorage` saved through jsonkit's `[@@deriving json]`, checked by a model-based law over real DOM events. Meltea gains `Sub.hash`, `Cmd.focus` and `Cmd.port`; subscriptions are typed by their source. Controlled inputs: `value` and `checked` are put back after input when the state did not take it, as in React, for both Meltea and Melact.
- Benchmark and the first half of P0: `bench/` measures the keyed js-framework-benchmark operations against vanilla JS and React 18. The runtime calls its own closures directly (`[@u]`), keeps no `lazy` and no bounds checks, uses `Js.null` positions and a closed type of states; `sandbox` no longer pulls in `Sub` and `Cmd`; handlers are guarded by the values they read; swapped ends of a keyed list are found without sorting, and a list that fills its parent is cleared with one `textContent = ""`. The counter is 3.0 kB gzip with Meltea and 5.6 kB with Melact.
- Compiled keyed loops: `Html.list (List.map row xs)` compiles to `View.each`, which reuses a row whose item is physically the same and whose outer variables (found by expanding local definitions) did not change, without calling `row`. Meltea is 1.09× vanilla JS on the keyed benchmark, Melact 1.10×, React 18 1.42×. `React.element` and `Html.t` are abstract, with `%identity` conversions for generated code.
- Server rendering and hydration: `Served.render` writes HTML with markers around dynamic parts, `Served.hydrate` takes it over (blocks adopt their nodes, lists from the last item back, the compiled walk skips marked ranges) and falls back to a render on a mismatch. `Program.render` / `~start:Program.hydrate` in Meltea, `ReactDOMServer.renderToString` / `ReactDOM.Client.hydrateRoot` in Melact. The browser path only pays a small `View.medium` record: Meltea's counter grows by 65 bytes.
- Less memory per row: a handler hole is one record with its property key computed once per event type, delegated handlers register no cleanup, and the keyed loop no longer keeps row descriptions (it marks rows as kept or fresh while patching); `Reconcile.plan` finds old keys in a small open-addressing table instead of sorting them. 1,000 rows take 1.67 MB of heap in Meltea (was 2.04) and 1.74 MB in Melact (was 2.20).
- Laws for the Vapor-like parts: the keyed loop under random edits (patch equals mount; with the order kept, exactly the rows whose item or projection changed are rendered; an outer change no projection sees writes nothing), pure components (renders and remounts exactly when inputs or identity change), and the reconciler on edit-shaped inputs. Nine mutants of these mechanisms are all caught.
- An optional typed pass in `meltea-ppx` (`staged_pps … -- -typed`): it types the rewritten file with compiler-libs and warns where a view reads a model field that can change in place; the JavaScript of TodoMVC is the same with and without it.
- Getting more out of the ppx: the field analysis reads `update` through helper `let`s and through a wrapper, and finds the masks of another module (`open!` over a fallback, with `analysed == M.update` checked once), so TodoMVC is tracked; the Rules of Hooks are checked by the type checker through a `hook` alert on every React hook, re-enabled by `melact-ppx` in branches, loops and callbacks.
- Keyed loops patch in place when the keys keep their order (no plan, a position only for rows that changed), and `Reconcile.plan` returns at once when one side is empty: clearing 1,000 rows went from 1.34× to 1.16× vanilla JS.
- Meltea's compiler reads `update` and `view` for the model fields each message changes and the view reads; a message that changes nothing the view reads does not call the view.
- Components without hooks compile to `View.pure`, with no instance: creating 1,000 rows in Melact went from 1.45× to 1.04× vanilla JS. Keyed benchmark: Meltea 1.16×, Melact 1.17×, React 18 1.64×.
- melhole knows no components: instances, hook slots, context and the scheduler moved to Melact's `melact.runtime`, built on melhole's open child protocol. Melact's `React.array (Array.map …)` compiles to the same keyed loop and selector as Meltea's lists.
- Compiled selectors, after Vue Vapor: the compiler splits a row into the pieces that read outer variables and re-renders only the rows whose pieces changed; selecting a row re-renders two rows.
- `React.Event`, as reason-react 0.14+ declares it, replaces the old `ReactEvent`: every family, read straight from the native event. Delegated handlers see the element they were set on as `currentTarget`, as in React. One law sends random mouse and keyboard events that handlers prevent or stop, and React 18 and Melact must read the same values.
- `React.createElement Foo.make (Foo.makeProps ~label ())`: melact-ppx writes `makeProps` next to every `[@react.component]` (and its `val`), as a call to `make` with a key. `ReasonReactRouter` with reason-react's API. Laws for both run against React 18 and Melact.
- reason-seoul's TodoMVC (reason-react with hooks, `useReducer`, a hand-written context provider, `ReasonReactRouter`) runs on Melact with only its `dune` file changed: `compat/run.sh` walks it randomly five times, 605 steps of clicks, typing, submits and route changes, and React 18 and Melact show the same DOM after every step. Controlled `value` keeps the `value` attribute in step, as React does.
- Transitions, as Vue's `<Transition>` and `<TransitionGroup>`: `Html.transition ~name` and `Html.transition_group ~name` in Meltea, over `Melhole.Transition`. Enter and leave classes, the leaving element kept in place until its transition ends, moves slid with FLIP in a group, the time from `~duration` or the computed style. A hosted child, so apps that do not animate carry none of it (the counter stays 3873 bytes). Seven laws in jsdom with fake timers, and fifteen mutants, all caught.
- Compiled rows: a keyed row that is one lowercase element with a `key` compiles to `View.rows`, whose rows are one record each (`Mounted_row`: root, scope, holes and a `Type.Id` witness) with the refresh called directly; no child description, `with_key` or mounted-child closures per row. Benchmark (Meltea, 1,000 rows): heap 1.68 → 1.40 MB, allocations while creating −34%; replace, partial update, select, clear and append are faster; creating from an empty list now meets a garbage collection inside its window, and its style and layout slow down with the marking, which is what the next steps on memory target. `bench/run.mjs --alloc` samples allocations per function.
- Flat holes: compiled text, attribute and handler holes are the bare node, element and event key; the last written value lives in a slot of the scope's `deps` (`put_text`, `put_attr`, `put_handler`, `listen`). A benchmark row loses its five hole records: 1,000 rows take 1.31 MB in Meltea (1.68 before compiled rows). Two new laws: a hole is written exactly when its value changes and an attribute that becomes `None` goes; an element's own listener for a non-bubbling event goes with it.
- Linked handlers in Meltea, after Inferno's `linkEvent`: an event prop compiles to one handler per site, hoisted to module level (`View.link`), and the element carries only the locals the message reads (`View.put_linked`); the handler reads them from `currentTarget` and builds the message at the click. A benchmark row no longer allocates two closures. Creating 1,000 rows allocates 481 kB (939 before compiled rows), 1,000 rows take 1.23 MB, replace went from ×1.30 to ×1.14 vanilla and the geometric mean from 1.17 to 1.14. A law clicks inside buttons of a list that changes under it and through `Html.map`, and checks every message.
- No closures per item in the loop patch, and no `Curry` in the runtime's hot loops: `compare_inputs`, the browser's `built`, the projections at mount and the in-place path are hand-written loops instead of `Array.for_all2`, `Array.init`, `Array.map` and `Array.mapi`, whose callbacks Melange calls through `Curry`. In profiles of select and partial update `Curry._2` had been the largest single cost.
