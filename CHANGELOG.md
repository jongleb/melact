# Changelog

## Unreleased

- The staged, typed stanza is the default: `docs/migration.md`, the README and Meltea's README
  recommend `(staged_pps melange.ppx melact-ppx -- -typed)` (and the same for `meltea-ppx`), still
  two lines of dune; plain `pps` keeps working with fewer optimizations. Every benchmark app, the 30
  apps and 18 repros of bench/classics, the SSR, resume and prerendered pairs (server sides too),
  the examples and the ratchet's programs build that way; the test suites stay on `pps`, and
  `compat/run.sh` builds the reason-react apps with the new stanza plus one TodoMVC under `pps`.
  Nothing in that corpus uses another module's component in a row or another module's custom hook,
  so the bundles and the ratchet's counters are unchanged (bench/meltea is 11 bytes smaller); a
  clean build of those trees took 189 s against 178 s (medians of four, on a loaded machine).
  `bench/meltea` keeps its rows in an array copied on every change and turns the `mutable_model`
  alert off.
- Melact's scheduler keeps the page's order of the instances a round's writes put off, instead of
  finding it again with `compareDocumentPosition` and a `TreeWalker`: a keystroke over 2,000 rows
  that read their own `offsetTop` takes no DOM steps (6,001 before), and the event table walks 84,356
  nodes (305,503). A component whose only read of the world is a ref it made reads the page
  (`Graph.Reads_the_page`) and keeps its update graph. A `createRoot` client no longer links
  hydration and resume: every Melact bundle is 0.3 to 1.3 kB gzip smaller.
- Less per row and less code, from what the compiler knows: `key=(string_of_int e)` keys a compiled
  row by the int (`Reconcile.int_key`) and `Html.int`/`React.int` texts go to the DOM as numbers
  (`Dom_api.shown_int`), so no number strings are made and V8's 64 kB cache of them never fills;
  definitions lifted for a row function that a loop compiled again are dropped; a delegated handler
  is one lifted definition, as `Events.delegate` now gives the handler's key. Every bundle the size
  ratchet measures is smaller, by up to 0.3 kB gzip. A release law checks with `WeakRef`s that a
  cleared loop keeps nothing it made.
- Dead messages and dead handlers: `meltea-ppx` alerts at a message nothing in the file sends
  (`dead_message`) and at a handler whose every message leaves the model as it is and runs no command
  (`dead_handler`). A message whose branch changes no field no longer queues a draw: ten of the
  ratchet's Meltea programs queue 1 to 3 fewer microtasks.
- Meltea's update graph: `meltea-ppx` reads what each branch of `update` does to each field (kept,
  set to one of a few constants, or set), through helpers, model-valued `let`s and a `match` on
  `(message, …)`. After the mount `Program` calls the view's slice, its page without the statements
  it does not read, with the fields written since the last draw, and every hole of a template there
  is evaluated only when a field it reads was written; a gate no message can close is not emitted.
  On the ratchet's Meltea runs view calls fall from 237 to 94 and hole evaluations from 222 to 104.
- `melact.meltea`, a migration path from hooks to Meltea: `<MelteaProgram program input onReport />`
  runs a Meltea program inside a Melact app (props become messages, messages are reported to
  callbacks, the view is drawn in Melact's flush), and `MelactHtml.element` puts a Melact widget into
  a Meltea view. Both run on the one melhole of the build. `docs/migration.md` is the guide;
  `examples/halfway` and `meltea/examples/migrated` are the same app halfway and at the end.
  `melact-ppx -meltea-hints` names, with an alert, every component whose only hooks are `useState`
  and `useReducer`.
- Melact renders on a server without a DOM: `melact-ppx -server` with `melact.server` (Melange, in
  Node) or `melact.server.native` (native OCaml) writes byte for byte what React 18's
  `renderToString` and `renderToStaticMarkup` write, `useId` and Suspense included, and Melact's
  client hydrates it with the same ids. A 1,000-row page takes 0.26 ms natively and 0.15 ms in Node,
  React 1.1 ms.
- Hydration and resume take the server's nodes over without writing them again: a template whose
  holes are all on elements needs no off-page clone, and `-hydratable` templates leave alone values
  the server's nodes already show. Melact hydrating bench/ssr's 1,000 rows went from 1,001
  attribute writes, 2,005 text writes and 8,012 created nodes to 1, 4 and 12, as React 18 does.
- Pages rendered at build time: `melhole-prerender` puts the HTML a native `-server` build prints
  into `index.html`, with the capture script, and the client resumes it with `Program.resume` or
  `ReactDOM.Client.resumeRoot`. On js-framework-benchmark's runner the benchmark apps paint first in
  70 ms (Meltea) and 72 ms (Melact), vanilla JS in 80 ms; mounted, they took 125 and 164 ms.

## 0.1.0

The first release.

- melhole: views compiled at build time to DOM templates with holes, each hole guarded by `===` on
  the values it reads; keyed loops that re-render only the rows whose item changed; server rendering
  in React's HTML format, natively or in JavaScript, and hydration.
- Melact (`melact`, `melact-ppx`): reason-react 0.17's API without React: components and every hook,
  context, `ReactDOM` and `ReactDOMServer`, `ReasonReactRouter`, `ReasonReactErrorBoundary`,
  `React.Suspense`, React 19's experimental hooks, `ReactDOMTestUtils`, and bindings to npm's
  `react` rewritten to Melact's own functions. An app moves over by changing two lines of `dune`.
- Meltea (`meltea`, `meltea-ppx`): the Elm architecture in mlx, with a compiler that reads `update`
  and `view` to re-render only what a message changed, commands, subscriptions and transitions.

## Before 0.1.0

How the five packages got here, step by step.

- Milestone 1: `melact.view` (templates with holes, hole patcher, keyed reconcile, delegated events), `melact.program` sandbox, hand-written counter example, 26 vitest + jsdom tests.
- Milestone 2: component instances and hooks (`Hook` keys, `Component`, `Context`, microtask flush, effects), `React`, `ReactDOM.Client`; the same test suite passes against reason-react with React 18 and against melact.
- Milestone 3: `melact-ppx` for Reason, OCaml `[@JSX]` and mlx: one template per JSX tree, hook keys per call site, `[@react.component]` and signatures; expect tests in `test/ppx`.
- Runtime trimming: no `Printf`, `Hashtbl` or `Map` in the bundle; keyed lookup by sorted keys. The counter app went from 23.4 kB to 10.2 kB gzip.
- A runtime made of parts: every kind of child carries its own mount and patch code, every hole its own `put_*`, and the component scheduler is installed by the first component. Unused parts drop out of the bundle: the counter app is 5.7 kB gzip with Meltea and 7.5 kB with Melact.
- Compiled walks: the compiler writes out the `firstChild`/`nextSibling` walk to every hole and picks HTML or SVG parsing, so the runtime keeps no paths and no tag table. The counter app is 4.2 kB gzip with Meltea and 5.9 kB with Melact.
- Direct writes: the compiled walk makes typed holes once per clone and the refresh writes them with `set_text`, `set_attr` and friends; no binding table, no indices. The counter app is 4.0 kB gzip with Meltea and 5.7 kB with Melact.
- TodoMVC in Meltea (`examples/todomvc`): routing, editing, `localStorage` saved through jsonkit's `[@@deriving json]`, checked by a model-based law over real DOM events. Meltea gains `Sub.hash`, `Cmd.focus` and `Cmd.port`; subscriptions are typed by their source. Controlled inputs: `value` and `checked` are put back after input when the state did not take it, as in React, for both Meltea and Melact.
- Benchmark and the first half of P0: `bench/` measures the keyed js-framework-benchmark operations against vanilla JS and React 18. The runtime calls its own closures directly (`[@u]`), keeps no `lazy` and no bounds checks, uses `Js.null` positions and a closed type of states; `sandbox` no longer pulls in `Sub` and `Cmd`; handlers are guarded by the values they read; swapped ends of a keyed list are found without sorting, and a list that fills its parent is cleared with one `textContent = ""`. The counter is 3.0 kB gzip with Meltea and 5.6 kB with Melact.
- Compiled keyed loops: `Html.list (List.map row xs)` compiles to `View.each`, which reuses a row whose item is physically the same and whose outer variables (found by expanding local definitions) did not change, without calling `row`. Meltea is 1.09× vanilla JS on the keyed benchmark, Melact 1.10×, React 18 1.42×. `React.element` and `Html.t` are abstract, with `%identity` conversions for generated code.
- Server rendering and hydration: `Served.render` writes HTML with markers around dynamic parts, `Served.hydrate` takes it over (blocks adopt their nodes, lists from the last item back, the compiled walk skips marked ranges) and falls back to a render on a mismatch. `Program.render` / `~start:Program.hydrate` in Meltea, `ReactDOMServer.renderToString` / `ReactDOM.Client.hydrateRoot` in Melact. The browser path only pays a small `View.medium` record: Meltea's counter grows by 65 bytes.
- Less memory per row: a handler hole is one record with its property key computed once per event type, delegated handlers register no cleanup, and the keyed loop no longer keeps row descriptions (it marks rows as kept or fresh while patching); `Reconcile.plan` finds old keys in a small open-addressing table instead of sorting them. 1,000 rows take 1.67 MB of heap in Meltea (was 2.04) and 1.74 MB in Melact (was 2.20).
- Laws for the Vapor-like parts: the keyed loop under random edits (patch equals mount; with the order kept, exactly the rows whose item or projection changed are rendered; an outer change no projection sees writes nothing), pure components (renders and remounts exactly when inputs or identity change), and the reconciler on edit-shaped inputs. Nine mutants of these mechanisms are all caught.
- An optional typed pass in `meltea-ppx` (`staged_pps … -- -typed`): it types the rewritten file with compiler-libs and warns where a view reads a model field that can change in place; the JavaScript of TodoMVC is the same with and without it.
- The same typed pass for `melact-ppx`, shared by both in `melhole.typed`: the untyped rewrite leaves questions (`[@melhole.ask n]`) and sites (`[@melhole.site n]`) with the functions that decide them; after every rewriter the file is typed and the sites decided, and a file that does not type keeps the untyped output exactly. Queries: `Mutability` (`Immediate`, `Immutable_boxed`, `Mutable_inside`, `Unknown`), now also behind Meltea's alert, and `Typed.component` (`Compiled`, `Of_props`). First use: a binding to npm's `Fragment` whose type expands to a component of children becomes Melact's fragment. The dual suite and the reported apps compile to the same JavaScript with and without it; a probe types every variable argument of the dual suite and checks the `Immediate` ones at run time; native laws check both queries on generated declarations; 33 mutants are caught.
- Getting more out of the ppx: the field analysis reads `update` through helper `let`s and through a wrapper, and finds the masks of another module (`open!` over a fallback, with `analysed == M.update` checked once), so TodoMVC is tracked; the Rules of Hooks are checked by the type checker through a `hook` alert on every React hook, re-enabled by `melact-ppx` in branches, loops and callbacks.
- Keyed loops patch in place when the keys keep their order (no plan, a position only for rows that changed), and `Reconcile.plan` returns at once when one side is empty: clearing 1,000 rows went from 1.34× to 1.16× vanilla JS.

- Hooks that reason-react 0.17 declares and React 18 has: `useInsertionEffect4` to `7`, `useSyncExternalStoreWithServer` (the client reads its own snapshot and hydration patches what differs), `useDeferredValue` with `~initialValue` (Melact renders without interruption, so it is the value) and `useTransitionAsync`; npm bindings to `useDeferredValue` and to a three-argument `useSyncExternalStore` are rewritten too. A dual law checks them under React 18 and Melact; two mutants are caught. reason-react's `useTransitionAsync` cannot start a transition under React 18 itself: React's start function has `length` 2, so Melange's `Curry._1` applies it partially.
- `ReactDOMTestUtils`, as reason-react 0.17 has it: `act`, `actAsync`, `Simulate` (each sends the native event Melact's handler for the prop listens to: `change` is `input`, `focus` is `focusin`, `blur` is `focusout`; `...WithEvent` lends the event its fields, and its `target.value` or `target.checked` is written to the element), `DOM.value` and the `findBy…` helpers, `prepareContainer`, `cleanupContainer`, `getContainer`, `isElement`, `isDOMComponent` and `isCompositeComponent` (always false: no class components). `isElementOfType` raises, since an element keeps no component type. A dual law drives a page through them in random order under React 18 and Melact; two mutants are caught.
- Bindings to npm React's element functions, from a user report: `createElement` from `"react"` (children as arguments or a `[@mel.variadic]` array), `jsx`, `jsxs` and `jsxDEV` from `"react/jsx-runtime"` (with or without a key) and `Fragment` no longer reach npm's React when they return `React.element`: they become `Melact_npm.created`, where a string tag builds a DOM element from the plain props object and a component is called with its props and children, as React does. A binding that returns a type of its own is left alone, as a deliberate use of npm React. A dual law renders a page through every shape under React 18 and Melact; an expect test pins the report's binding. `React.act` also puts controlled inputs back at once, as React does, instead of two microtasks later (found by the `ReactDOMTestUtils` law).
- Eight findings from a user, each now a test (`test/regress`, built as the report builds: Reason, `(pps melange.ppx melact-ppx …)`):
  hooks are found under `open React` and `React.( … )`, through a module of the file that includes React, and through `-hook-modules` for one in another file;
  a custom hook polymorphic in its value compiles, because a call site's key is hoisted as `unit Hook.key` and used through `Hook.unchecked` (the order of hooks is still checked);
  a `[@react.component] external` to a JavaScript React library's component is a clear compile error instead of a confusing one;
  `dangerouslySetInnerHTML` compiles whatever order the ppx run in, because the compiler reads `__html` through `Melhole.View.html_of` instead of writing `##`;
  the generated props type is `make_props`, so a file's own `type props` no longer clashes;
  `ReactDOM.Ref.t`, `currentDomRef` and `callbackDomRef` exist;
  melact-ppx's npm rewrite is an instrumentation run before the other rewriters, not a whole-file preprocessor, so it sits next to another ppx that has one (server-reason-react.ppx);
  and a binding to npm's `Fragment` with a type of its own is left alone again.
- `ReactDOM.Experimental`'s resource hints as React 19 does them on the client: `preconnect`, `prefetchDNS`, `preload` (nothing without `as`), `preloadModule`, `preinit` (a script, or a stylesheet placed after the last one of its precedence) and `preinitModule` add their tag to the head once per resource. A law checks random sequences against a model of React 19's head; a mutant that ignores precedence groups is caught. Every `as` value carries `[@mel.as]`: when only `object` did, as in reason-react's declaration, Melange turned every other value into `undefined`.
- A file that starts with `include React;`, the usual shape of a module of hooks in reason-react code, has its hooks found as under `open React`, in components and in custom hooks alike (from the same user; a regression test builds such a file).
- React 19's `React.Experimental`: `useTransitionAsync` (pending while its async action runs), `useOptimistic` (an action's updates on top of the state) and `useContext`; async actions are entangled as React 19 entangles them, so every action stays pending and every optimistic update stays until all running actions have settled (found with a probe of React 19). `useActionState` is minimal: reason-react 0.17's binding types its action as returning nothing and gives a `formAction` no form accepts. `usePromise` and `promise` wait for Suspense. A new dual suite runs on React 19 (`test/dual19`, its own React in `test/dual19/env`, mapped by `vite.config.js`), and the rest stays on React 18; its law clicks and releases concurrent actions against a model, and a mutant without entanglement is caught. npm bindings to `useOptimistic`, `useActionState` and `use` of a context are rewritten too.
- `React.Suspense`, with React 19's `use` of a promise (`React.Experimental.usePromise`) and `React.Experimental.promise`: a component reading a pending promise suspends; the nearest boundary shows its fallback; content that has never been shown is dropped and built again, and content already shown stays in the DOM, hidden (`display: none !important`, emptied text) with its state, as React hides it; an update to a waiting boundary renders its children again, and the boundary waits on the newest promise. The boundary is installed by its first use, next to error boundaries, so apps without one do not carry it (the benchmark bundle grows by 0.2 kB raw, the timings do not move). A dual law on React 19 resolves, replaces and pre-resolves promises and clicks a counter inside the boundary; five mutants are caught.
- Two fixes found on the way, for error boundaries too. An exception thrown inside JSX (the compiler evaluates hole expressions while the template is built or updated) is now caught like one thrown before it: the `try` covers a component's build and update as well as its render. And a render that throws halfway through its holes makes its template forget the values it last read (`View.forget`), so the next render evaluates every hole again instead of skipping the one whose guard had already recorded the new value. The error-boundary law gains bombs that throw from inside their JSX.
- From the same user, each with a test in `test/shadowed` (a build with `-open Shadow`, whose `Option`, `Array`, `List`, `String`, `Printf`, `Fun`, `Int` and `Float` are empty): a typed optional prop with a default (`?(tone : Tone.t = A)`, Reason's `~tone: Tone.t=A`) compiles, because the alias melact-ppx adds goes inside the type constraint, so the default is typed by it; the code both ppx generate names `Stdlib.Option`, `Stdlib.Array` and `Stdlib.List`, so a project's own modules under those names no longer break it, and `Stdlib.Array.map` and `Stdlib.List.map` compile to keyed loops as `Array.map` and `List.map` do; `onLoad` is in the DOM prop table (`<img onLoad>`, a `React.Event.Image`), the one prop of reason-react's `domProps` that was missing.
- A build that contains reason-react next to Melact (a library in the emit's closure that requires reason-react) used to compile against one `React` and could import the other, leaving hooks `undefined` with only a bundler warning. Every file melact-ppx compiles now calls `React.reason_react_is_also_in_this_build_remove_it ()`, which only Melact's `React` has: such a build fails to compile with that name, or, if only the JavaScript import went to reason-react's file, fails as the module loads with the same name. The README says how to fix it.
- Three more from the same user. Custom CSS properties (`--gap` through `ReactDOM.Style.unsafeAddProp`) are written with `setProperty` and removed with `removeProperty`, as React does, instead of a `style[name]` assignment that ignores them; the server writes their names as they are, without turning capitals into dashes. `children == React.null` (structural equality) works: `React.null` carries a `TAG` of its own, so Melange's `equal` and `compare` tell it from any other element before they reach the functions an element holds. A dual law sets, changes and removes a custom property beside an ordinary one under React 18 and Melact, and another compares children with `React.null` both ways round; a mutant of each is caught. Reading `props` back from an element cannot be supported without giving every element a props object; the README now says so and what to do instead.
- From a user's real app: a controlled `<input>` lost what was typed on a real keyboard, in Melact and Meltea alike. The value was put back by a listener on the element itself, two microtasks later; a trusted event runs a microtask checkpoint after every listener, so the restore ran before the delegated handler read `event.target.value`. jsdom's `dispatchEvent` runs no microtasks between listeners, so no test saw it. Now, as in React, the delegated listener puts controlled values back after it has delivered the event (`change` is delegated too), and a controlled element registers that delegation even without a handler. `test/browser/typing.mjs` types into accepting, transforming and truncating controlled inputs of both libraries with real key events in headless Chrome; it fails on the old code with every field empty, passes now, and runs in CI.
